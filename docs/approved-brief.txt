The website should serve global visitors while accurately distinguishing US-specific rules, regional calculations, currencies, units, and tax years.

Prioritize:
- Calculation accuracy.
- Complete calculator coverage.
- A polished, accessible user experience.
- SEO: search engine optimization.
- GEO: generative engine optimization.
- AEO: answer engine optimization.
- Fast loading and reliable operation.
- Modular code and low operating costs.

5. CALCULATOR ACCURACY AND FUNCTIONALITY

Implement real, deterministic calculations. Do not use an LLM to produce numerical results.

For every calculator:
- Validate required inputs and meaningful limits.
- Handle invalid, empty, zero, negative, and extreme values appropriately.
- Use suitable numerical precision and documented rounding.
- Explain assumptions, limitations, and supported use cases.
- Support relevant units and input modes.
- Provide readable results and useful interpretation.
- Add reset, print, comparison, or export features where appropriate.

Verify formulas against authoritative sources. Competitor outputs may be comparison points, but must not be the only evidence of correctness.

Use versioned datasets and explicit effective dates for tax brackets, contribution limits, statutory rules, and other changing data. Show the selected jurisdiction and year.

Changing a currency symbol must not silently change a tax system or mortgage convention.

For live data such as exchange rates, document the provider, timestamp, caching, licensing, and unavailable-data behavior.

Write meaningful automated tests for every calculation engine, covering known examples, boundary conditions, invalid inputs, and relevant mathematical properties. Include independent expected results rather than reproducing the implementation inside the tests.

For financial and health tools, provide clear limitations and appropriate informational disclaimers. Never invent professional review, credentials, or scientific validity.

Identify entertainment-only calculators honestly.

7. BACKEND AND COST REQUIREMENTS

First determine which features actually require a backend or database.

Prefer browser-side calculation engines and version-controlled content where suitable. Do not add accounts, a database, or a separate backend merely because they are common in web applications.

If server functionality is necessary, prefer an appropriately simple implementation integrated with Next.js unless a separate service has a clear benefit.

The database pricing requirement is strict:
- No mandatory monthly subscription or minimum spend.
- No required $20–$25 starting plan.
- A usage-based paid path that can start at $0 when no billable usage occurs.
- Usage billed afterward where supported.
- A clear explanation of storage, operations, bandwidth, backups, and other charges.

A free tier alone does not satisfy this requirement if the upgrade path introduces an unavoidable monthly base fee.

Before choosing a provider, verify current official pricing, commercial-use terms, production limitations, and billing behavior. Compare suitable options and document the decision.

Evaluate hosting costs separately and disclose any fixed fees.

Provide low-, medium-, and higher-traffic cost estimates with explicit assumptions. Include caching, rate limits, and budget alerts where supported.

Keep sensitive calculator inputs out of analytics, logs, and persistent storage by default. Shareable calculation links should be an explicit user action with an appropriate privacy explanation.

- Crawlable page explanations and meaningful initial page content.

Use structured data only when it accurately describes visible content and complies with current documentation. Distinguish valid schema vocabulary from eligibility for Google search features.

Verify current search feature support. Do not invent ratings, reviews, authors, credentials, or special “GEO” markup.

For answer and generative search:
- Give concise, direct explanations.
- Define terms, formulas, assumptions, and units clearly.
- Include useful examples and readable comparison tables.
- Cite primary sources.
- Make important content available as text.
- Use clear headings and meaningful section anchors.
- Keep terminology and organization consistent.
- Make authorship and editorial responsibility truthful.

Do not treat llms.txt, FAQ markup, structured data, or any single technical feature as a ranking guarantee.

Research search intent, competition, and useful long-tail opportunities. Prioritize implementation and content work intelligently while retaining the full catalog commitment.

Use genuine regional variants where formulas, rules, or content differ. Add hreflang only for real equivalent localized pages. Avoid mass-producing near-identical country pages.

Prepare a practical launch and growth plan covering Search Console, sitemap submission, index monitoring, content maintenance, and measurement.

Aim for the fastest responsible route to discoverability and sustainable traffic. Do not promise first-page rankings, indexing deadlines, AI citations, or advertising income.

9. PERFORMANCE, ACCESSIBILITY, AND ADS

Design mobile-first and verify mobile, tablet, laptop, and large-screen layouts.

Target WCAG 2.2 AA accessibility, including:
- Keyboard navigation.
- Visible focus.
- Proper labels and error messages.
- Accessible dialogs and menus.
- Screen-reader-friendly results.
- Adequate contrast.
- Reduced-motion support.
- Text or table alternatives to charts.

Target good Core Web Vitals:
- LCP at or below 2.5 seconds.
- INP at or below 200 milliseconds.
- CLS at or below 0.1.

Treat these as field performance targets at the 75th percentile. Use lab testing before launch and real-user measurements after sufficient traffic exists. Report actual measurements and test conditions.

Optimize fonts, images, JavaScript, caching, and third-party scripts.

Prepare reusable ad placements with reserved space to prevent layout shifts. Ads must not obscure inputs, results, or navigation.

Keep ad integration configurable. Use real publisher identifiers only when supplied, and implement applicable consent and privacy controls based on the actual integrations and target markets.

Do not send calculator values to advertising or analytics services by default.
